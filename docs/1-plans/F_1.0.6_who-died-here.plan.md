# Who Died Here Implementation Plan

> **Status note**: TRIP remains uninitialized (no ARCHI.md); this plan documents its own context, per F_1.0.0–F_1.0.2 precedent. Decided 2026-09-13: "who died here" = Wikidata **P20 (place of death)** as a second discovery mode beside the existing **P119 (place of burial)**. Ships as **1.0.6** (`package.json` + `expo.version` tick together in TRIP-3). The `NEARBY_LIMIT` cap discussion is explicitly **out of scope** — separate decision after this ships.

## Overview

Explore gets a two-way mode toggle — **Buried here / Died here** — above the radius chips. "Died here" runs the same nearest-first SPARQL pipeline against place of death instead of place of burial, so hospitals, homes, battlefields and hotels show up as pins with the notable people who died in them. Cards, section headers, the person page and saved rows stop assuming every place is a grave.

## Problem Statement

- `buildQuery` hardcodes `wdt:P119`; the `Soul.place` field is semantically "resting place" everywhere it's rendered ("Resting at", "souls rest here", "No notable burials", "Unknown resting place").
- Saved favorites snapshot `place` without saying what kind of place it is. A soul saved in died-mode would render "Resting at: Denver General Hospital" — a false statement.
- Visits are defined as *grave* visits (rank credit, "get within half a mile of a grave"). A death-place coordinate must not silently become a grave visit.

## Solution Architecture

One new discriminator flows through the whole stack: `SoulMode = "buried" | "died"` at query time becomes `Soul.placeKind: "burial" | "death"` on every result, is copied into `FavoriteSoul`, and every string that today says "rest/buried/grave" branches on it. Old favorites (no `placeKind`) normalize to `"burial"` at read time — the same defensive-read pattern as `visitStampOf`.

The query also fetches the **complementary** place label (burial place in died-mode, death place in buried-mode) as `Soul.otherPlace`, so the person page can state both facts when Wikidata has both.

**Decisions taken here (override if wrong):**
1. Mode is **session state** in Explore (`useState`, default `"buried"`), not persisted. Cheapest; revisit if usage shows people live in died-mode.
2. **Visits stay grave-only.** On a `placeKind === "death"` soul the person page renders no visit control at all (save + directions still work). Rationale: visits feed ranks and the procession flywheel; a hospital lobby isn't a grave.
3. A favorite is keyed by qid; whichever mode it was first saved from wins its `placeKind`. Toggle-off then re-save from the other mode replaces it. No merge logic.

## Implementation Details

### 1. Query layer — `src/lib/wikidata.ts`

**Current state**: `buildQuery(lat, lon, radiusKm)` with `?person wdt:P119 ?p.` at line ~59; `fetchNearbySouls(lat, lon, radiusKm)`; `Soul` has no place-kind.

**Modifications**:
- `export type SoulMode = "buried" | "died"`; `export type PlaceKind = "burial" | "death"`; `export const placeKindOf = (mode: SoulMode): PlaceKind`.
- `Soul` gains `placeKind: PlaceKind` and `otherPlace: string | null`.
- `buildQuery(lat, lon, radiusKm, mode: SoulMode = "buried")`: predicate line becomes `?person wdt:${mode === "died" ? "P20" : "P119"} ?p.` Comment the swap. Outer query adds `OPTIONAL { ?person wdt:<the other predicate> ?other. }`, projects `?otherLabel` (label service handles it), adds `?otherLabel` to the outer `GROUP BY`. A person with two burial places multiplies rows — existing first-row-wins qid dedup already absorbs that (same as multi-image today).
- `fetchNearbySouls(lat, lon, radiusKm, mode: SoulMode = "buried")`: passes mode through; sets `placeKind: placeKindOf(mode)`, `otherPlace: r.otherLabel?.value ?? null`. Unknown-place fallback becomes mode-aware: `"Unknown resting place"` / `"Unknown place of death"`.
- **Died-mode "legit place" filter (decided 2026-09-13):** inside the subquery, died-mode only, add `FILTER NOT EXISTS { ?p wdt:P1082 [] }` right after the P20 triple. Wikidata records most deaths at city precision ("Denver"), and the city item has one coordinate — Denver at 25 km returned 148/150 rows on the centroid. Excluding places that carry a population (cities, counties, CDPs) leaves venues: hospitals, Stapleton, Denver Zoo. Measured live: 0.7 s Denver/25 km, 1.4 s Denver/90 km, 9.6 s Paris/25 km. The "correct" `wdt:P31/wdt:P279* wd:Q56061` admin-entity path was 20–38 s — over the fetch timeout, don't retry it. Buried-mode gets no filter. Mia's rule: "if there's a legit place we show it."
- `groupByCemetery` unchanged (it's grouping by place string; the name is now a misnomer — leave it, rename is churn).

### 2. Hook — `src/hooks/use-nearby-souls.ts`

- `useNearbySouls(lat, lon, radiusKm, mode: SoulMode)`; `queryKey: ["nearby-souls", mode, lat, lon, radiusKm]` so the two modes never share a cache entry.

### 3. Favorites — `src/lib/favorites/types.ts`, `src/lib/favorites/local-repository.ts`, `src/lib/sync/remote.ts` (read path)

- `FavoriteSoul` gains `placeKind?: PlaceKind` (optional: rows written before 1.0.6 lack it, in AsyncStorage and in the `favorites.soul` jsonb column — no migration).
- `toFavorite` copies `placeKind` and `otherPlace` (`otherPlace?: string | null`, optional for the same reason).
- Add `placeKindOfFav(fav): PlaceKind` next to `visitStampOf` — returns `"death"` only when the field is exactly that string, else `"burial"`. **The one place the default is decided.**
- Person page reconstructs a `Soul` from `FavoriteSoul` via route params today (JSON in `data`); the parse guard in `person/[qid].tsx` must default `placeKind` through `placeKindOfFav` and `otherPlace` to `null`.

### 4. Explore — `src/app/explore.tsx`

- `const [mode, setMode] = useState<SoulMode>("buried")`; pass to `useNearbySouls`; add `mode` to `settledKey` so a mode flip scrolls the list to top like a radius change does.
- **Toggle UI**: a two-segment row between `PlaceSearch` and the radius chips, same chip recipe (34pt, white-fill active, glass inactive), `accessibilityRole="button"` + `accessibilityState={{ selected }}`, labels **"Buried here"** / **"Died here"**. Both flex:1. `Keyboard.dismiss()` on press like the radius chips. `headerH` is measured via `onLayout` already, so the sheet's collapsed height self-corrects.
- Copy branches on `mode`:
  - walk-up sub-line: `"souls rest here"` → `"souls died here"`.
  - status row (uncapped): `notable souls within X` stays; add nothing — the toggle states the mode.
  - `ListEmptyComponent`: `"No notable burials in this radius."` → `"No notable deaths in this radius."`
  - Back button a11y label `"Back to all nearby cemeteries"` → `"Back to all nearby places"` (mode-neutral).
- **Died-mode explainer (decided 2026-09-13, copy pinned verbatim):** a dim 12pt line directly under the toggle, died-mode only: `Only souls whose death has a recorded spot — a hospital, a hotel, a battlefield. A city alone doesn't count. Know one we're missing? Add it on Wikidata — it's what this map reads.` "Wikidata" is a tappable inline link to `https://www.wikidata.org/` (opens externally). Died-mode empty state: `No recorded death spots in this radius. Try widening it.`
- Map: no change. Pins are places; the callout shows the place title.

### 5. Person page — `src/app/person/[qid].tsx`

- Stat label `"Resting at"` → `soul.placeKind === "death" ? "Died at" : "Resting at"`. When `soul.otherPlace` is set, pass it as the `Stat`'s `sub` prefixed the other way round: died-mode `sub="Buried at {otherPlace}"`, buried-mode `sub="Died at {otherPlace}"`. `Stat` already renders `sub`.
- `renderVisitAction()`: first guard — `if (soul.placeKind === "death") return null;` with a comment pointing at decision 2.
- **Contribute link (decided 2026-09-13):** under the stat grid, both modes, a small external-link row `Improve this record on Wikidata` → `https://www.wikidata.org/wiki/<qid>` via `Linking.openURL`. Upstream contribution, not in-app UGC — consistent with strategy "Nopes".
- Directions `q=` already uses `soul.place` — correct for both.

### 6. Saved / favorite row — `src/components/favorite-row.tsx`, `src/app/saved.tsx`

- Row sub-line `[years, fav.place]` — prefix death places so the dig list is honest: `placeKindOfFav(fav) === "death" ? \`died · ${fav.place}\` : fav.place`. Keep it that small.
- `saved.tsx` empty copy ("get within half a mile of a grave") stays — visits are grave-only.

### 7. Tests

- `src/lib/wikidata.test.ts`: `buildQuery` uses `wdt:P119` by default and `wdt:P20` for `"died"`; the P1082 filter appears only in died-mode; the complementary `OPTIONAL` uses the other predicate; `fetchNearbySouls` stamps `placeKind` per mode and reads `otherLabel`; unknown-place fallback per mode; existing `NEARBY_LIMIT` tests untouched.
- `src/lib/favorites/types.test.ts`: `toFavorite` carries `placeKind`/`otherPlace`; `placeKindOfFav` defaults missing/garbage to `"burial"`.

## Technical Considerations

- **Density**: P20 clusters far harder than P119 (one hospital = hundreds of notable deaths). The capped path (`capped`, results-box framing, "nearest souls" header) already handles it; expect the cap to bite at smaller radii than burials do. Out of scope here; feeds the cap discussion.
- **Label service + OPTIONAL other place**: adding `?otherLabel` to the outer GROUP BY is the only query-shape change; the subquery (the expensive part) is untouched, so latency stays ~3s in dense cities.
- **Backward compat**: every new field is optional on the persisted shape and defaulted at read. No Supabase migration.
- **Web**: `souls-map.tsx` (web placeholder) and `app-tabs.web.tsx` carry no burial copy — grep `rest|buried|grave` before closing to be sure.
- **Edge cases**: soul with no coord in died-mode (P20 item lacks P625) is excluded by `wikibase:around` exactly as today. A person whose death place *is* their burial place (died in the cemetery) shows the same string in both stat slots — fine.

## Addendum 2026-09-14 — radius honored (added during test pass)

Mia's test: 90 mi in Denver buried-mode showed the same downtown cluster as 5 mi. Fix shipped in 1.0.6: `buildQuery` inner query = UNION of nearest-first pass (LIMIT `NEARBY_LIMIT` 150) and an outer-ring pass (`FILTER(?d > 0.25·R && ?d <= R)`, `ORDER BY MD5(STR(?person))`, LIMIT `OUTER_RING_LIMIT` 90). Two passes only — each `wikibase:around` pass scans all burials in radius (Paris/145 km: 4 passes 22 s, 3 passes 17 s, 2 passes 7 s). Explore: header always "within X", map always the radius box; cap-aware framing removed. This closes the "creative rate limiting" thread for radius; viewport-driven querying stays a separate idea.
