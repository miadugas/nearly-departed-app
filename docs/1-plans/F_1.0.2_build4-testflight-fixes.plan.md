> **Status note**: TRIP remains uninitialized (no ARCHI.md); this plan documents its own context, per F_1.0.0/F_1.0.1 precedent. Source: `docs/testflight-feedback.md` items 1 and 3 (item 2 was backend-only and is already fixed). Repo version bumps to 1.0.2 in `package.json` during TRIP-3 release (step 8 of that skill); App Store marketing version stays 1.0.0 — this ships as iOS build 4 via EAS remote auto-increment.

## Overview

Two user-facing fixes from the pre-submission TestFlight pass: (1) an **editable display name** on the profile screen so a signed-in user's identity line isn't an Apple private-relay address (`78pw929rcr@privaterelay...`), synced to the account the same way the avatar is (user decision 2026-08-18: sync, not local-only); (2) **human error copy** on the auth screen when sending a sign-in code fails, replacing the raw JSON currently rendered (`{"status":500,...}`).

## Problem Statement

- With Sign in with Apple + Hide My Email, the profile header renders the relay address as the user's identity — accurate but user-hostile, and the first thing every privacy-conscious tester sees.
- `src/app/auth.tsx` renders `e.message` verbatim (lines ~148/163/177). When the backend fails at the HTTP level, supabase-js messages can be entire JSON response bodies — which testers saw during the SMTP outage.

## Solution Architecture

**Display name** follows the avatar's local-first + best-effort-mirror architecture, with two deliberate departures forced by the fact that a *name* is account-identity rather than device flair:

1. **User-scoped storage, not one global key.** Guest names live at `nd:display-name:guest`; a signed-in user's name lives at `nd:display-name:u:<userId>`. Without this, signing out of account A and into account B shows (and then pushes) A's name — a cross-account identity leak, and worse for a name than for an avatar. A guest name is **promoted once** on first sign-in, but only *after* the profile fetch confirms the account has no name of its own (an existing account name always wins); the guest key is left intact for future guest sessions. On sign-out the provider drops the in-memory name back to the guest key's value (the existing avatar behavior is untouched — out of scope).
2. **Three-state local value, so "Clear" survives offline.** The stored value distinguishes *never set* (key absent → `undefined`) from *explicitly cleared* (key holds a tombstone → `null`) from *named* (string). `mergeDisplayName` adopts a remote name only when local is `undefined`; a local `null` means the user cleared it and the reconcile pushes the clear instead of resurrecting the remote value. Without the tombstone, clearing a name while offline silently comes back on next reconcile.

The existing `AvatarProvider` (`src/lib/avatar/context.tsx`) is extended to own both profile fields rather than adding a third provider — one storage load, one reconcile pass, one `profiles` fetch serving both values. Its context value gains `displayName`/`setDisplayName`; `useAvatar` and the `_layout.tsx` wiring are unchanged.

**Friendly auth errors**: `friendlyAuthMessage(e, { policy })` maps caught errors to human copy with an **operation-specific policy** — `"fixed"` for send-code and Apple sign-in (the raw message is never rendered, full stop) and `"allowlist"` for verify-code, which passes through only messages matching known-human auth strings (invalid/expired token) and otherwise falls back. Raw errors go to `console.warn` under `__DEV__` only.

## Implementation Details

### 1. Database migration — `profiles.display_name`

**File**: `supabase/migrations/0003_display_name.sql` (new)

`alter table public.profiles add column if not exists display_name text;` with a header comment matching 0001/0002 style (run in the Supabase dashboard SQL editor — ops step, not applied by code). Existing own-row RLS policies (0001) already cover the new column; no policy changes.

### 2. Remote I/O

**File**: `src/lib/sync/remote.ts`

**Current state**: `fetchAvatar` selects only `avatar_id`; `upsertAvatar` upserts `{id, avatar_id, updated_at}`.

**Modifications**:

- Replace `fetchAvatar` with `fetchProfile(userId)` returning `{ avatarId: string | null; displayName: string | null }` from one `select("avatar_id, display_name")` — one round trip serves both reconciles. (Internal rename; update the one caller.)
- Add `upsertDisplayName(userId, name | null)` mirroring `upsertAvatar` — payload `{id, display_name, updated_at}`. PostgREST upsert uses merge-duplicates semantics (only provided columns update on conflict), so avatar and name pushes cannot clobber each other; note this in a comment since it's load-bearing.
- `upsertAvatar` unchanged.

### 3. Merge logic + name sanitation

**File**: `src/lib/sync/merge.ts`

- Add `mergeDisplayName(local: string | null | undefined, remote: string | null)`, returning `{ effective: string | null; pushLocal: boolean }`. Three-state local semantics: `string` → keep local, push it; `null` (explicit clear tombstone) → effective `null`, push the clear so an offline Clear is not resurrected; `undefined` (never set on this device) → adopt sanitized remote if any, no push.
- Add `sanitizeDisplayName(raw: string | null | undefined): string | null` — trim, collapse inner whitespace runs, strip control characters, cap at 40 characters, empty → `null`. Single source of truth used by the provider (both directions) and the profile editor.

### 4. Provider — extend avatar context to profile fields

**File**: `src/lib/avatar/context.tsx`

**Current state**: single-value provider (see file header comment); loads `nd:avatar`, reconciles once per signed-in user, fire-and-forget pushes.

**Modifications**:

- Add `displayName: string | null` state, persisted under a **scoped key**: `nd:display-name:guest` when signed out, `nd:display-name:u:<userId>` when signed in. Stored payload encodes the three states — key absent = never set; the literal tombstone value (e.g. JSON `null` / a sentinel constant defined once in this module) = explicitly cleared; otherwise the sanitized name. A tiny read/write pair (`readStoredName`/`writeStoredName`) keeps the encoding in one place.
- Guest name loads at startup (before `isReady`); on sign-in the effect re-reads under the user-scoped key.
- `setDisplayName(name)` is the **user-intent path only**: sanitize → state + write-through to the currently active scoped key (tombstone on null, never a bare key removal) → `upsertDisplayName` fire-and-forget when signed in. Reconcile must never call it (see below).
- A separate **reconcile-only apply path** (`applyReconciledName(effective, { persist })`) sets state and writes storage without ever pushing remotely and without forging a tombstone: adopting a remote name writes the name to the user-scoped key; an `effective` of `null` arising from `undefined` local + empty remote **leaves the key absent** (still "never set"), so a later remote name can still be adopted and no spurious clear is pushed. Only a `pushLocal` result from the merge may trigger `upsertDisplayName`.
- Reconcile effect (per signed-in user, existing guard), strict ordering to avoid clobbering an existing account name:
  1. Read the user-scoped local value (three-state).
  2. `fetchProfile(userId)` once; sanitize the remote name.
  3. **Promotion, only if both hold**: user-scoped local is `undefined` **and** the sanitized remote name is empty — then adopt the guest name as local (write it to the user-scoped key) and push it. If the account already has a name, no promotion: the account name wins and is adopted locally.
  4. Otherwise run `mergeDisplayName(local, remote)` and apply via the reconcile-only path; push only when `pushLocal`.
  5. `mergeAvatar` continues to use the same `fetchProfile` response, unchanged.
  The guest key is never deleted or overwritten by this flow.
- On sign-out (`userId → null`, where the effect currently only resets the reconcile guard): reset in-memory `displayName` to the guest key's value so account A's name never shows — or gets pushed — under a later session.
- Context value/type gains the two members; update the header comment to say the provider owns the profile's device-local fields (avatar + display name).

### 5. Profile screen — show + edit the name

**File**: `src/app/profile.tsx`

**Current state**: header `<Text>` shows `signedIn ? email : "Guest"` (~line 361); avatar picker is a slide-up `Modal` bottom sheet (`AvatarPickerModal`, ~lines 150–236).

**Modifications**:

- Header text becomes `displayName ?? (signedIn ? email : "Guest")`. When a display name is shown for a signed-in user, render the email underneath in the existing dim caption style so account identity is never hidden.
- **Avatar initial** (~line 273, currently derived from `email`) must derive from `displayName ?? email` — otherwise a Hide My Email user fixes their name and still stares at a "7" from the relay prefix.
- New `NameEditorModal` following the `AvatarPickerModal` idiom (transparent slide-up `Modal`, bottom sheet, uppercase section label "What should we call you?"): a `TextInput` (`maxLength={40}`, autofocus, `returnKeyType="done"` submitting the save, dark styling per screen idiom), Save and Clear actions; Save runs `sanitizeDisplayName` and calls `setDisplayName`; Clear writes the tombstone (header falls back to email/Guest).
- **Keyboard avoidance is required**, since this sheet (unlike the avatar grid) autofocuses a text field: wrap the sheet in `KeyboardAvoidingView` (`behavior="padding"` on iOS) so Save/Clear stay above the keyboard, and verify on device.
- Edit affordance: pressing the name line opens the editor (accessibilityRole button, label "Edit display name"). Works for guests too.

### 6. Auth screen — friendly send-code errors

**File**: `src/app/auth.tsx`

**Current state**: three catch blocks set `error` to `e.message` with generic fallbacks; raw server messages (including JSON bodies) render in the error slot.

**Modifications**:

- Extract a pure, unit-testable helper `friendlyAuthMessage(e: unknown, opts: { policy: "fixed" | "allowlist"; fallback: string }): string` into `src/lib/auth/messages.ts`. Policy is **per call site**, so the send-code guarantee cannot be weakened by a permissive shared rule:
  - `policy: "fixed"` — always returns `fallback`; the caught message is never rendered.
  - `policy: "allowlist"` — returns the caught message only if it matches a short list of known-human auth strings (case-insensitive match on invalid/expired token phrasing, and only when brace-free and under ~80 chars); otherwise `fallback`.
- Send-code catch (~line 163): `policy: "fixed"`, copy "Couldn't send the code. Try again in a minute — or use Sign in with Apple."
- Apple catch (~line 148): `policy: "fixed"`, existing fallback copy retained (the cancel-detection branch above it is untouched).
- Verify-code catch (~line 177): `policy: "allowlist"`, fallback "That code didn't work."
- All three log the raw error via `if (__DEV__) console.warn` before setting state.

## Technical Considerations

- **Pattern Usage**: Everything mirrors the established local-first + best-effort-mirror pattern (avatar/favorites). No new architecture.
- **Upsert clobber risk**: separate single-field upserts are safe **only** under PostgREST merge-duplicates; the comment in remote.ts must warn future editors not to "simplify" into a whole-row upsert.
- **Privacy surface**: display name is user content synced to the account → privacy policy and App Store label must mention it (see Documentation Impact). Apple's label taxonomy: covered as **Name** (Contact Info) — add to the published label (collected, linked, App Functionality, no tracking).
- **Account deletion**: `profiles` cascade already wipes `display_name` — no change to the delete-account function.
- **Edge Cases**: whitespace-only or control-char-only names (sanitize → null); 40-char cap enforced at input *and* in sanitize (paste bypasses `maxLength` on some keyboards); guest sets a name then signs in to a nameless account (promoted once, pushed); guest signs into an account that already has a name (account name wins — no silent overwrite); user clears the name while offline (tombstone holds, clear pushes on next reconcile instead of resurrecting); account A signs out, account B signs in (B reads its own scoped key — A's name never displays or pushes); name set on device B while device A is offline (last push wins — accepted v1 semantics, same as avatar); remote name garbage/empty (ignored by merge).

## Performance & Cost Impact

Neutral: reconcile still makes one `profiles` round trip (previously avatar-only, now both fields). One extra AsyncStorage read at startup.

## Backward Compatibility

- Older builds (build 3) ignore `display_name` entirely — additive column, no breakage.
- Pre-migration server + new client: `fetchProfile`/`upsertDisplayName` error on the missing column; all sync errors are already swallowed (local-only behavior), so the app degrades exactly like today. Migration is still a pre-release ops step so sync works from day one.

## Test Impact

- New pure functions need unit tests (vitest, alongside existing merge tests): `sanitizeDisplayName` (trim, whitespace collapse, control chars, 40-char cap, empty → null); `mergeDisplayName` across the full three-state matrix — **including the two Codex-flagged regressions**: local `null` (cleared) + remote name → effective null with `pushLocal` true (never resurrect), and local `undefined` + remote name → adopt without push; `friendlyAuthMessage` for both policies (fixed policy never returns the caught message even when it looks human; allowlist passes an expired-token string but falls back on a JSON body).
- Existing `mergeAvatar`/`mergeFavorites` tests unaffected; the `fetchAvatar → fetchProfile` rename touches no test (remote.ts has no unit tests — network seam, per coverage policy).
- Critical-path floor: name sync touches persistence and account identity — merge/sanitize tests cover the decision logic; the storage-scoping and promotion wiring is verified manually (below) since it lives in a provider effect.
- Manual integration checks (simulator): set name → relaunch → persists; clear name **offline** → relaunch/reconcile → stays cleared; **guest name + sign in to an account that already has a name → the account's name wins** (guest value does not overwrite it); guest name + sign in to a nameless account → promoted and pushed; sign out of account A → sign in as B → B does not show A's name; fresh sign-in with no name anywhere → header falls back to email and the storage key stays absent (a name later set on another device is still adopted); send-code failure with airplane mode → friendly copy, no JSON; name editor with keyboard open → Save/Clear reachable.
