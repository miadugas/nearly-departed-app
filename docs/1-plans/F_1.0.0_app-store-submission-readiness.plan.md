# App Store Submission Readiness Implementation Plan

> **Status note**: Parts of Phase 1–2 were applied to the working tree during initial triage (before this plan was formalized). Those items are pre-checked in the To-dos and still subject to this review — nothing is committed yet. TRIP is not yet initialized in this repo (`/TRIP-init` pending, user-invocation only), so there is no ARCHI.md to conform to; this plan documents its own architectural context.

## Overview

Prepare Nearly Departed 1.0.0 (Expo SDK 56 / React Native 0.85, expo-router, Supabase auth, CNG — `ios/` and `android/` are gitignored prebuild artifacts) for its first App Store submission. Three workstreams: (1) make `app.json` the complete source of truth for a clean EAS/prebuild iOS build (Apple Sign In entitlement, encryption compliance, honest permission strings); (2) satisfy App Review Guideline 5.1.1(v) by adding in-app account deletion end-to-end (Supabase Edge Function → auth context → profile UI → privacy policy); (3) stand up EAS Build + Submit as the delivery path, iPhone-only.

## Problem Statement

- **Sign in with Apple is gated OFF and would break on any clean build.** `src/app/auth.tsx` hard-codes `APPLE_SIGN_IN_ENABLED = false` (it was disabled pending paid Apple Developer Program membership — now resolved: Team `CJAFZA5NP9`, per the Pharaday project's signing config). Separately, the `com.apple.developer.applesignin` entitlement exists only in the local, gitignored `ios/NearlyDeparted/NearlyDeparted.entitlements`; neither `ios.usesAppleSignIn` nor the `expo-apple-authentication` config plugin was declared in `app.json`, so EAS (which runs prebuild from a fresh checkout) would produce a binary whose Apple sign-in fails at runtime. **Decision (user, 2026-08-16): ship Apple sign-in in 1.0** — enable the flag, keep the entitlement config, and take on the revocation obligation below.
- **Apple token revocation on account deletion.** Apple requires apps offering Sign in with Apple to revoke the user's Apple tokens when their account is deleted. The current sign-in discards Apple's `authorizationCode`, and the deletion function only deletes the Supabase user — no revocation path exists.
- **No in-app account deletion.** The app supports account creation (email OTP + Sign in with Apple via Supabase). The privacy policy says "email us to delete" — Guideline 5.1.1(v) requires deletion be initiable inside the app; this is one of the most common 1.0 rejections.
- **Encryption compliance unanswered.** Without `ITSAppUsesNonExemptEncryption`, every App Store Connect upload prompts for an export-compliance answer.
- **Boilerplate purpose strings.** Prebuild's generated Info.plist carries expo-location's defaults ("Allow $(PRODUCT_NAME) to access your location") for `NSLocationAlwaysUsageDescription`, `NSLocationAlwaysAndWhenInUseUsageDescription`, and `NSMotionUsageDescription`. The app only ever requests when-in-use, but generic strings on present keys are a known rejection/metadata-review irritant (Guideline 5.1.1).
- **Privacy policy contradicts actual data flows.** `legal/privacy-policy.md` states favorites "stay on your device and are not uploaded to your account" — but when signed in, favorites and the chosen avatar id ARE mirrored to Supabase (`src/lib/favorites/context.tsx`, `src/lib/avatar/context.tsx`, migration `0001_account_sync.sql`). The policy (local + hosted) and the App Store privacy labels must describe the sync truthfully.
- **No build pipeline.** `eas.json` exists (remote versioning, production autoIncrement) but the repo has no EAS `projectId`, and `eas-cli` isn't installed on this machine.

## Solution Architecture

Keep everything config-driven so CNG stays intact: no manual edits to `ios/` (it is disposable). Account deletion follows the only shape Supabase allows from a client app — the client cannot delete its own `auth.users` row, so a server-side **Edge Function** (`delete-account`) verifies the caller's JWT and deletes the user with the service-role key; FK `on delete cascade` from `auth.users` already wipes `public.profiles` and `public.favorites` (migration 0001). On-device favorites are intentionally untouched (they are device-local by design). The client exposes this via a new `deleteAccount()` on the existing `AuthContext`, and the profile screen adds a destructive, double-confirmed "Delete account" action visible only when signed in.

### 2. Account deletion — server (incl. Apple token revocation)

**File**: `supabase/functions/delete-account/index.ts` (new; base version already drafted, revocation to be added)

Deno Edge Function, POST-only. Resolves the caller from the `Authorization` header using an anon-key client (so a user can only ever identify — and therefore delete — themselves), then deletes that user via a service-role client's `auth.admin.deleteUser`. Cascades handle `profiles`/`favorites`. Returns JSON errors with proper status codes (405/401/500). Platform-injected `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

**Apple revocation extension** (required because Apple sign-in ships in 1.0): when the request body carries an `appleAuthorizationCode`, before deleting the user the function:

1. Builds the Apple client-secret JWT with `npm:jose` — ES256 signed with the Sign in with Apple `.p8` key; header `kid` = `APPLE_KEY_ID`, `alg` = ES256; claims `iss` = `APPLE_TEAM_ID`, `iat` = now, `exp` = now + ≤15 min (Apple allows up to 6 months; short-lived per call is fine), `aud` = `https://appleid.apple.com`, `sub` = client id = bundle id `com.miadugas.nearlydeparted`.
2. Exchanges the code: `POST https://appleid.apple.com/auth/token`, `application/x-www-form-urlencoded` body `client_id`, `client_secret`, `code`, `grant_type=authorization_code`.
3. **Binds the code to the caller**: decodes the returned `id_token` and requires its `sub` to equal the caller's Apple identity id (the `apple` entry in the Supabase user's `identities`, whose `provider_id`/`sub` is the Apple user id). On mismatch: skip revocation, report `revoked: false, reason: identity_mismatch` — never revoke a token that isn't provably the caller's.
4. Revokes: `POST https://appleid.apple.com/auth/revoke`, form-encoded `client_id`, `client_secret`, `token` = the returned `refresh_token`, `token_type_hint=refresh_token`.

Revocation is **best-effort**: failure never aborts the deletion — Guideline 5.1.1(v) makes deletion availability the harder requirement, and a user whose Apple re-auth fails must still be able to delete their account. But per Apple TN3194 the outcome is surfaced, not swallowed: the response carries `revoked: true/false`, and when `false` for an Apple-linked user, the client's success alert appends manual-revocation instructions (Settings → [your name] → Sign-In & Security → Sign in with Apple → Nearly Departed → Stop Using).

**New Supabase secrets** (set once via `supabase secrets set`): `APPLE_TEAM_ID=CJAFZA5NP9`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (contents of a Sign in with Apple key created in the Apple Developer portal).

**Deploy step (manual, needs Supabase CLI login)**: `supabase functions deploy delete-account` against project `lazmmkvavwicxophadmt`. Also verify the Supabase Auth Apple provider is configured with the bundle id as client id.

### 3. Account deletion — client state

**File**: `src/lib/auth/context.tsx`

**Current state**: `AuthContextValue` exposes `sendCode` / `verifyCode` / `signInWithApple` / `signOut`.

**Modifications**: Add `deleteAccount()` — invokes the `delete-account` function via `supabase.functions.invoke` (which attaches the session JWT automatically), then clears the local session with a local-scope sign-out (a global sign-out would 4xx because the server-side user no longer exists). Session/user state resets through the existing `onAuthStateChange` listener; no screen changes needed for state propagation.

**Apple revocation hook**: if the signed-in user's `identities` include provider `apple` (and platform is iOS), `deleteAccount()` first runs `AppleAuthentication.signInAsync` to obtain a fresh `authorizationCode` (Apple codes are single-use, 5-minute expiry — they cannot be stored at sign-in time without also persisting refresh tokens server-side, which we deliberately avoid) and passes it in the invoke body. If the user cancels or the Apple sheet fails, deletion proceeds without the code. `deleteAccount()` returns the server's `revoked` status so the profile screen can append the TN3194 manual-revocation instructions to the success alert when revocation didn't happen for an Apple-linked account.

## Technical Considerations

- **CNG discipline**: every native requirement must live in `app.json` plugins/fields; the local `ios/` dir is a build artifact. Verification uses `npx expo config --type introspect` rather than mutating `ios/`.
- **Security of deletion endpoint**: JWT-scoped self-identification (anon client + caller's Authorization header) before any service-role action; POST-only; no user-supplied target id — deleting *other* users is structurally impossible.
- **Auth state propagation**: rely on the existing `onAuthStateChange` — no ad-hoc session clearing in screens.
- **Apple revocation trade-off**: re-auth at deletion time (fresh `authorizationCode`) instead of persisting Apple refresh tokens server-side — stateless, no token storage surface; cost is one extra Apple sheet during deletion for Apple-linked users, and revocation degrades to best-effort if that sheet is cancelled.
- **Edge cases**: delete while offline (surface failure alert, account intact); Apple sheet cancelled mid-deletion (deletion proceeds, revocation skipped); email-only users (no Apple hook at all); re-signup after deletion creates a fresh user (profiles row auto-created by existing signup path); deletion succeeding but local sign-out failing (handled: local sign-out failure is swallowed — listener still fires on next refresh failure, and worst case the stale session 401s and the app treats it as guest).

## Test Impact

- Existing vitest suite doesn't cover auth context (verify: `npm test` stays green).
- New logic worth a unit test: none client-side beyond thin wrappers around Supabase calls; the edge function's auth gating (missing/invalid Authorization → 401, non-POST → 405) and the Apple client-secret builder are the testable core if a Deno test harness is introduced — otherwise covered by `deno check` + manual verification.
- Manual/integration checks: `npx expo config --type introspect` shows the entitlement + Info.plist keys and that `tsc`/`expo lint` pass with the Deno boundary excluded.
- **Deletion proof, not just appearance**: record the signed-in user id before deleting, then verify via SQL (service role / dashboard) that `auth.users`, `public.profiles`, and `public.favorites` hold **zero rows** for that id — the UI returning to guest state is not sufficient because local favorites are intentionally retained and would re-upload on next sign-in, masking a failed server deletion.
- Apple round trip: sign in with Apple → delete account (expect the Apple confirmation sheet) → verify revocation response ok + rows gone → fresh Apple sign-in shows the full consent sheet again (evidence the token was revoked).
