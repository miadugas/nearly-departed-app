# Supabase Keep-Alive Cron Implementation Plan

> **Status note**: TRIP is still not initialized in this repo (no ARCHI.md); like F_1.0.0, this plan documents its own context. A working draft of the workflow already exists **uncommitted** at `.github/workflows/supabase-keepalive.yml` (written and ping-tested 2026-08-17, HTTP 200 against the live project); this plan formalizes it for review before it is committed.

## Overview

Add a scheduled GitHub Actions workflow that pings the Supabase project (`lazmmkvavwicxophadmt`) so the free-tier database is very unlikely to reach its ~7-day inactivity auto-pause. Supabase defines the reset threshold loosely ("a few database requests per day" is typically sufficient — [free-project-pausing docs](https://supabase.com/docs/guides/platform/free-project-pausing)), so this is deliberately best-effort risk reduction, not a guarantee; Pro tier remains the only contractual fix. A paused backend silently breaks sign-in, email OTP, favorites/avatar sync, and the `delete-account` edge function — and would fail App Review if the pause lands mid-review. Decisions (user, 2026-08-17): the cron lives **in this repo** (not a separate repo, not an external pinger), and failure alerting is **GitHub's built-in failed-run email** (no auto-issue creation).

## Problem Statement

- **Free-tier Supabase pauses after ~7 idle days.** It has already happened once (project was INACTIVE on 2026-08-17 and had to be manually restored). While paused, all auth and REST calls fail; the app degrades to local-only and sign-in is impossible.
- **The pause is silent.** Supabase emails the owner, but nothing in the repo or app surfaces it; the first real signal would be a user (or App Review) failing to sign in.
- **App Review window is the acute risk.** A submission can sit in review for days; if the backend pauses during that window, rejection is likely.

## Solution Architecture

A single GitHub Actions workflow with a twice-daily `schedule` trigger (`23 3,15 * * *` — two runs so a full day of activity survives one skipped run, minute 23 because GitHub explicitly warns that top-of-hour crons are the most likely to be dropped) plus `workflow_dispatch` for manual testing. Each run issues **several PostgREST queries** — exactly `profiles?select=id&limit=1` and `favorites?select=user_id&limit=1` (`favorites` has no `id` column; its primary key is `(user_id, qid)` per migration 0001) — authenticated with the **publishable anon key** — Supabase counts *database* activity and describes "a few requests per day" as typically sufficient, so the pings must reach Postgres (not an edge/health endpoint) and one lone request should not be assumed to clear the bar. RLS returns zero rows to an anonymous caller, so the requests leak nothing. Any non-200 fails the job, which triggers GitHub's failed-workflow email to the repo owner. Curl gets explicit connect/total timeouts and the job a small `timeout-minutes` cap so an outage fails fast (GitHub's default job timeout is 360 minutes — an unbounded hang would delay the failure email by hours).

Placement rationale (decided): a dedicated repo would itself go inactive and hit GitHub's 60-day scheduled-workflow disablement for public repos faster than this actively developed repo; an external pinger avoids that rule but adds an unmanaged third-party account. This repo is the least-worst home, with the 60-day rule accepted as a documented caveat.

**Current state**: Draft exists and has been validated by running its curl command manually (HTTP 200). Not yet committed; inert until pushed to the default branch.

**Modifications**:

- Pin the schedule to `23 3,15 * * *` (twice daily, off the top of the hour — GitHub documents that start-of-hour crons are the most likely to be delayed or dropped).
- Expand the single query to a loop over the two pinned queries — `profiles?select=id&limit=1` and `favorites?select=user_id&limit=1` — so each run produces "a few" database requests, matching Supabase's documented activity threshold; every response must be 200 or the job fails.
- Add `--connect-timeout 10 --max-time 30` to curl and `timeout-minutes: 2` on the job so a hung backend fails (and emails) within minutes, not GitHub's 360-minute default.
- Keep `workflow_dispatch` so the request path can be verified manually right after push.
- Keep the anon key inline (it is the same publishable key already committed in `app.json` — no secret hygiene gained by a repo secret, and inline keeps the workflow self-contained).
- Keep the fail-on-non-200 exit so failures reach the owner via GitHub email (decided alerting path).
- Comment block must state the caveats: 60-day public-repo cron disablement — GitHub emails a warning first, and recovery after disablement is **explicit** (Actions UI toggle, `gh workflow enable supabase-keepalive.yml`, or a commit that changes the cron expression; an ordinary unrelated push does *not* re-enable it) — and that pinging is best-effort, with Supabase Pro the only contractual fix.

## Technical Considerations

- **Pattern Usage**: First GitHub Actions workflow in the repo; nothing to conform to. YAML style follows GitHub's documented minimal form.
- **Activity semantics**: Supabase counts database activity and only commits to "a few database requests per day" being *typically* sufficient. The PostgREST queries hit Postgres through the connection pooler; auth-only endpoints (e.g. `/auth/v1/health`) may not count. Do not "simplify" the ping to a health endpoint or collapse it back to a single request. A green workflow still doesn't *prove* the pause clock reset — watch the Supabase owner-email channel for pause warnings regardless.
- **Key exposure**: The anon key is a publishable key guarded by RLS; it is already public in `app.json` in this public repo. No new exposure.
- **GitHub cron reliability**: Scheduled runs can be delayed or skipped; twice-daily cadence + 7-day pause budget absorbs multiple consecutive misses. `workflow_dispatch` covers manual recovery.
- **60-day rule**: Public-repo scheduled workflows are disabled after 60 days without repo activity. Accepted risk; development activity resets the clock and GitHub warns by email first. If disablement ever happens, re-enabling is an explicit act (Actions UI, `gh workflow enable`, or editing the cron line) — and a missed-ping → paused-project state is still recoverable by manual restore in the Supabase dashboard.
- **Edge Cases**: Project paused anyway (ping returns 5xx → job fails → email); Supabase maintenance windows (transient failure, the next scheduled run recovers); repo made private later (cron keeps running but consumes Actions minutes — negligible at ~2 min/day).
